# 06. 문제 해결 및 최종 구현 범위

## 구현 중 발생한 문제와 해결

### 1. 장시간 기록에 따른 데이터 누적

**문제**

16개 오브젝트의 Transform을 매 프레임 계속 보관하면 실행 시간이 길어질수록 데이터와 메모리 사용량이 증가합니다.

**해결**

`scr_TransformRecorder`에 프레임 보관 상한을 적용하고, 오래된 프레임을 제거하면서 최근 600프레임만 유지하는 순환형 기록 구조를 구성했습니다.

**결과**

장시간 실행 중에도 기록 데이터 크기가 일정 범위 안에서 유지되며, 최근 동작 구간을 지속적으로 확인할 수 있습니다.

### 2. 여러 오브젝트의 기록 데이터 관리

**문제**

각 오브젝트가 개별적으로 Transform 데이터를 관리하면 Overview, Detail, Focus 화면에서 대상 검색과 데이터 접근 방식이 달라질 수 있습니다.

**해결**

`scr_TransformRecorderManager`에서 기록 대상들을 수집하고 공통 접근 경로를 제공하도록 구성했습니다.

**결과**

16개 기록 대상의 데이터를 동일한 구조로 조회하고, 선택한 오브젝트의 기록을 각 화면에서 일관되게 사용할 수 있습니다.

### 3. 단계별 그래프 데이터 조회

**문제**

전체 현황과 개별 축 데이터를 같은 방식으로 갱신하면 불필요한 데이터 조회와 그래프 갱신이 반복될 수 있습니다.

**해결**

`scr_TransformGraphDataProvider`를 통해 기록 데이터 접근을 통합하고, Overview·Detail·Focus 단계에서 필요한 데이터만 조회하도록 분리했습니다.

**결과**

전체 오브젝트 현황부터 선택 오브젝트의 위치·회전 축까지 단계적으로 확인할 수 있습니다.

### 4. 실행 중 기록과 파일 저장 책임 분리

**문제**

Transform 기록, JSON·CSV 변환과 파일 저장을 하나의 클래스에서 처리하면 기록 로직과 저장 UI의 책임이 섞이고 저장 순간의 부하 원인을 확인하기 어렵습니다.

**해결**

기록은 `scr_TransformRecorder`, 통합 관리는 `scr_TransformRecorderManager`, 파일 저장은 `scr_TransformDataSaveLoadManager`, 저장 UI는 `scr_TransformFileBrowserUI`로 역할을 분리했습니다.

Unity Profiler를 사용해 JSON·CSV 저장 순간의 CPU·GC 사용량도 확인했습니다.

**결과**

실시간 기록과 파일 저장 흐름이 분리되어 기능별 동작과 성능을 독립적으로 확인할 수 있습니다.

## 최종 구현 범위

- 16개 오브젝트의 Position·Rotation 실시간 기록
- 최근 600프레임 순환 보관
- Overview·Detail·Focus 단계별 그래프
- 선택 오브젝트와 축별 데이터 조회
- JSON 형식 기록 저장
- CSV 형식 기록 내보내기
- 저장 파일 선택과 불러오기 UI
- Unity Profiler 기반 저장 순간 CPU·GC 점검
- 샘플 Transform 기록 데이터 제공

## 완료 상태

PLT Monitor는 교육 평가 프로젝트로 구현과 검증을 완료했습니다. 문서에 기록된 범위는 현재 저장소에 포함된 Unity 소스, 샘플 데이터와 검증 자료를 기준으로 정리했습니다.
