## 1. 장시간 실행에서 기록 데이터가 계속 증가하는 문제

| 구분 | 내용 |
| --- | --- |
| 상황 | 16개 오브젝트의 Transform을 매 프레임 기록하면 실행 시간에 비례해 메모리와 조회 비용이 증가합니다. |
| 원인 | 전체 실행 이력을 제한 없이 `List`에 누적하는 구조는 실시간 그래프가 실제로 사용하는 최근 구간보다 훨씬 많은 데이터를 보유합니다. |
| 해결 | 오브젝트별 Recorder에 최대 600개 프레임을 두고, 초과 시 가장 오래된 항목을 제거하는 rolling buffer를 적용했습니다. |
| 결과 | 현재 분석 범위를 `16 Objects × 600 Frames`로 고정하고 장시간 실행 시 무제한 누적을 막았습니다. |
| 배운 점 | 실시간 모니터링에서는 “모든 기록 보존”과 “현재 구간의 빠른 관찰”을 분리해야 합니다. 장기 보존은 파일 저장 계층의 책임으로 두는 편이 명확합니다. |

현재 구현의 선두 항목 제거는 데이터 규모가 더 커지면 비용이 커질 수 있습니다. 다음 단계에서는 고정 배열 기반 circular buffer로 교체할 수 있습니다.

## 2. 16개 그래프와 9개 수치를 한 화면에서 읽기 어려운 문제

| 구분 | 내용 |
| --- | --- |
| 상황 | 16개 오브젝트와 Position·Rotation·Scale XYZ를 동시에 펼치면 정보량이 지나치게 많아집니다. |
| 원인 | 전체 상태 탐색과 단일 축 분석을 같은 화면 밀도로 해결하려 했기 때문입니다. |
| 해결 | Overview에서 16개 전체를 스캔하고, Detail에서 선택 오브젝트의 X/Y/Z/All을 비교한 뒤, Focus에서 한 축을 확대하는 3단계 UX를 설계했습니다. |
| 결과 | 사용자가 전체 이상 후보를 찾은 후 필요한 범위만 점진적으로 좁힐 수 있게 됐습니다. |
| 배운 점 | 모니터링 UI는 데이터를 많이 표시하는 것보다 관찰 순서와 선택 문맥을 유지하는 것이 중요합니다. |

## 3. Save JSON/CSV 클릭 순간 CPU·GC spike

| 구분 | 내용 |
| --- | --- |
| 상황 | 일반 실행과 그래프 전환은 안정적이지만 Save JSON/CSV 클릭 시 FPS가 순간 하락하고 이후 회복했습니다. |
| 원인 | 최대 9,600개 프레임을 저장 DTO와 문자열로 구성하고 직렬화하는 작업이 메인 스레드에 집중되며 임시 할당과 GC를 유발합니다. |
| 시도 | 코루틴 기반 분할 저장도 검토했지만, 작업 총량과 할당 구조를 근본적으로 줄이지 못해 지속적인 FPS 유지에 충분하지 않아 보류했습니다. |
| 현재 판단 | 저장 결과는 정상이며 일반 실행 요구인 60 FPS 이상에는 문제가 없지만, 클릭 순간 병목을 known issue로 공개합니다. |
| 개선 방향 | 불변 스냅샷 생성 후 백그라운드 직렬화, 스트리밍 CSV 쓰기, 버퍼 재사용과 단계별 Profiler 측정을 적용합니다. |

![Profiler 캡처](../media/screenshots/profiler.png)

단순히 `async` 키워드를 붙이는 것으로 Unity API의 스레드 안전성이 해결되지는 않습니다. 메인 스레드에서는 Unity 객체에서 순수 데이터 스냅샷만 만든 뒤, 파일 형식 변환과 I/O를 안전한 작업 영역으로 넘기는 구조가 필요합니다.

## 4. 외부 아이콘 에셋이 저장소 크기와 재현성에 주는 문제

| 구분 | 내용 |
| --- | --- |
| 상황 | 로컬 `CleanFlatIcon` 에셋은 400MB 이상이지만 실제 핵심 UI에서 사용한 것은 그래프 point sprite 1개였고, 두 Prefab에서 총 5회 참조했습니다. |
| 원인 | 하나의 작은 마커 때문에 전체 외부 에셋 폴더가 프로젝트 의존성이 됐습니다. |
| 해결 | 투명 배경의 단순 원형 `Assets/Art/Graph/point_marker.png`를 프로젝트 내부에서 직접 만들고 5개 Prefab 참조를 모두 교체했습니다. 원본 폴더는 로컬 개발 환경에 유지하되 Git 추적에서는 제외했습니다. |
| 검증 | 기존 CleanFlatIcon GUID가 Unity YAML에 남지 않았고 핵심 기능이 외부 에셋 없이 참조를 해석하도록 정리했습니다. |
| 결과 | 당시 계산한 예상 Git 추적 크기가 약 252MB에서 약 16MB로 감소했으며, 새 clone에서 그래프 marker가 Missing Reference가 되는 위험을 제거했습니다. |

외부 패키지 전체를 저장소에 포함하기 전에 실제 참조 GUID와 필요한 최소 자산을 확인해야 한다는 점을 배웠습니다. 라이선스·재배포 범위, 저장소 용량, Unity GUID 안정성을 함께 관리한 사례입니다.
