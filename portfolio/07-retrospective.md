# 07. 회고

[← 포트폴리오 목차](README.md)

## 잘한 점

- 요구사항의 핵심 수치를 16 Objects, 600 Frames, Transform 9개 값으로 고정해 구현·샘플·QA 문서가 같은 기준을 사용하도록 했습니다.
- 기록, 조회, 표현, 파일 저장 책임을 분리해 하나의 데이터 원본을 세 그래프 모드에서 재사용했습니다.
- 기능 통과만 기록하지 않고 Profiler로 저장 순간의 병목을 확인해 known issue와 개선 방향을 함께 남겼습니다.
- 외부 에셋의 실제 GUID 참조를 확인한 뒤 내부 Sprite로 교체해 clone 재현성과 저장소 용량을 함께 개선했습니다.

## 배운 점

### 데이터 수집과 표현은 분리해야 한다

Recorder가 UI를 직접 갱신하면 그래프 종류와 저장 형식이 늘어날수록 결합이 커집니다. Recorder → Manager → DataProvider → Renderer/UI로 책임을 나누면서 같은 기록을 Overview, Detail, Focus와 파일 저장에서 재사용할 수 있었습니다.

### 모니터링 화면은 탐색 순서가 중요하다

16개 오브젝트와 9개 값을 한꺼번에 보여 주는 것보다 Overview에서 후보를 찾고 Detail과 Focus로 좁히는 흐름이 읽기 쉽습니다. 화면 수를 늘린 것이 아니라 사용자의 분석 단계를 정보 구조에 반영한 경험이었습니다.

### 정상 동작과 성능 품질을 따로 검증해야 한다

JSON·CSV 파일이 정상 생성된다는 사실만으로 저장 기능의 품질이 충분하지 않았습니다. Profiler를 통해 직렬화와 GC가 클릭 순간 프레임에 영향을 준다는 점을 확인했고, 기능 통과와 성능 known issue를 함께 기록했습니다.

### 외부 에셋은 실제 의존 범위로 관리해야 한다

400MB가 넘는 에셋 전체에서 Sprite 하나만 사용한 상황을 GUID 단위로 확인하고 내부 자산으로 대체했습니다. Unity에서는 파일을 단순히 빼는 것보다 `.meta` GUID와 Prefab 참조를 함께 검증해야 새 clone의 재현성을 지킬 수 있었습니다.

## 아쉬운 점과 한계

- rolling buffer가 `List` 선두 삭제 방식이어서 더 큰 규모에는 circular buffer가 적합합니다.
- 전체 저장 데이터 스냅샷과 문자열 직렬화가 메인 스레드에 집중됩니다.
- 상태 해석은 고정 규칙이며 실제 설비 기준이나 통계 모델과 연결되지 않았습니다.
- 선택 파일은 파싱하지만 Recorder와 그래프 상태를 복원하지 않습니다.
- 자동화 테스트보다 수동 QA 체크리스트 비중이 큽니다.

## 개선 방향

1. 고정 크기 circular buffer와 할당 최소화
2. Unity 객체 스냅샷과 백그라운드 직렬화·I/O 분리
3. 저장 진행률, 취소, 실패 복구와 원자적 파일 교체
4. 로드 데이터를 별도 세션 모델에 연결하는 Replay 모드
5. 데이터 형식 version field와 이전 버전 마이그레이션
6. Recorder·CSV 파서·Meaning Analyzer 단위 테스트
7. Object·Frame 수를 늘린 성능 기준과 자동 프로파일링

## 다음 프로젝트에 적용할 원칙

실시간 관제나 디지털 트윈 프로젝트에서는 화면을 만들기 전에 데이터의 소유자, 보존 범위, 갱신 주기와 유효성 기준을 먼저 정리하겠습니다. 또한 “연결됨”, “파싱됨”, “화면에 복원됨”을 서로 다른 완료 상태로 정의해 기능을 과장하지 않고 검증 가능한 결과로 설명하겠습니다.
